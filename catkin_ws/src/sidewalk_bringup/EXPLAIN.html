Phase 1 · sidewalk_bringup

Bringup — Starting the Robot's Nervous System

The single command that starts everything, and the map of how the robot's body parts relate to each other in space.

Ready to run

◆ In plain language

Think of a robot as a body. The camera is an eye, the wheels are legs, the computer is a brain. None of those parts are useful on their own — what makes a robot work is that they are connected, and that each one knows where the others are.

This package is that connection. It does two jobs. First, it is the "on switch": one command starts every piece of software in the right order, so you never have to remember which of nine programs to launch first. Second, it holds the robot's body map — a precise description of where the camera sits relative to the wheels, measured in millimetres.

That second job sounds boring. It is the single most common cause of a failed robotics experiment. If the software thinks the camera is 10 cm further forward than it really is, every measurement the robot makes will be wrong by 10 cm, and no amount of clever algorithm work will fix it.

Why this exists

A running robot is not one program. It is a dozen programs talking to each other at the same time — camera driver, mapping, navigation, logging. Starting those by hand is slow and easy to get wrong, and getting the order wrong produces confusing failures that look like algorithm bugs.

Centralising startup means an experiment can be reproduced exactly. That matters for research: a result nobody can reproduce is not a result.

The physical picture

For a mechanical engineer, the body map here is just a coordinate transform chain — the same thing you build when you stack reference frames in a CAD assembly. Each link in the chain says "frame B sits this far, and rotated this much, from frame A".

The robot's chain runs: world → map → odometry → robot base → camera mount → camera lens. Any error anywhere in that chain propagates to everything downstream, exactly like a tolerance stack-up in an assembly drawing.

And like a tolerance stack, the error that hurts you most is usually angular. A 1 degree mounting error in the camera's pitch does almost nothing to an object 10 cm away, but it displaces a point 20 m away by about 35 cm. This is why the mounting bracket's rigidity is a SLAM problem, not just a mechanical one.

What it actually does

  1. Defines every coordinate frame on the robot and how they relate, in a URDF description
  2. Publishes those relationships continuously so every other program can ask "where is the camera right now?"
  3. Provides one launch file per phase, so each stage of the project starts with a single command
  4. Centralises all tunable numbers into YAML config files instead of scattering them through code
  5. Sets up logging so every run leaves a permanent, timestamped record
  6. Runs a preflight check that refuses to start if something important is missing

Key ideas, explained twice

Once in everyday words, once in the technical terms you will meet in the literature.

Node
PlainlyOne running program that does one job — for example, the program that talks to the camera. A robot runs many at once.
TechnicallyAn executable process registered with the ROS master, communicating over TCPROS/UDPROS.
Topic
PlainlyA named channel that programs use to broadcast information. The camera publishes pictures to a channel; anyone who wants pictures listens to that channel. The publisher does not know or care who is listening.
TechnicallyA named, typed, many-to-many asynchronous message bus with publisher/subscriber semantics.
TF (transform) tree
PlainlyThe robot's body map — a live, constantly-updated record of where every part is relative to every other part.
TechnicallyA time-indexed directed tree of coordinate frame transforms, queryable at arbitrary timestamps with interpolation.
URDF
PlainlyA text file describing the robot's physical shape and dimensions — essentially a simplified CAD model the software can read.
TechnicallyUnified Robot Description Format: an XML schema for kinematic and visual robot models.
Launch file
PlainlyA recipe listing which programs to start, in what order, with which settings.
TechnicallyAn XML declaration of nodes, parameters, remappings and nested includes, executed by roslaunch.

Inputs and outputs

Takes in

  • config/robot_frames.yaml — the measured physical offsets between robot parts
  • config/camera_mount.yaml — where the ZED X sits and how it is oriented
  • Phase selection, chosen by which launch file you run

Produces

  • A live TF tree, published continuously on /tf and /tf_static
  • The robot model on /robot_description, which visualisation tools read
  • A timestamped run log in logs/sidewalk_bringup/
  • A preflight report saying whether the system is fit to run

How to run it

roslaunch sidewalk_bringup preflight.launch

Run this FIRST, every session. It checks the camera is detected, the transform chain is complete, disk space is sufficient and no clock skew exists — then tells you plainly whether you are safe to proceed. It changes nothing; it only reports.

roslaunch sidewalk_bringup bringup.launch

Starts the core system: robot description, transform publishers and logging. This is the foundation every other phase builds on.

roslaunch sidewalk_bringup bringup.launch camera:=true

The same, plus the ZED X camera driver. Use this once the camera is physically wired.

rosrun sidewalk_bringup hello_ros.py

A deliberately tiny teaching program. It publishes a counter, subscribes to it, and prints what it receives — demonstrating the publish/subscribe idea in about forty lines. Read the source; it is commented line by line.

rosrun rqt_tf_tree rqt_tf_tree

Draws the robot's body map as a diagram. Every frame should be connected to every other. A frame floating on its own means a transform is missing, and anything depending on it will silently produce wrong answers.

When it goes wrong

You see thisIt usually meansDo this
rqt_tf_tree shows a disconnected frameA transform in the chain is not being published, usually a typo in a frame nameCheck the frame names in config/robot_frames.yaml match exactly what the camera driver publishes. Names are case-sensitive and a trailing space will break them.
Everything starts but no data appears anywhereROS_IP is unset, so nodes advertise an address other machines cannot reachThis exact bug existed on the old system. bringup.launch now sets ROS_IP explicitly — verify with echo $ROS_IP.
roslaunch cannot find the packageThe workspace was not sourced in this terminalRun source ~/catkin_ws/devel/setup.bash, then try again. Every new terminal needs this.
Timestamps look wrong, or data is rejected as too oldClock mismatch between machinesPreflight checks this. Ensure both machines run NTP and agree to within a few milliseconds.
Preflight reports the camera is missingDriver not installed, camera not wired, or daemon not runningRun tools/health_check.sh for a full diagnosis — it distinguishes these three cases.

Where the logs go

Every run of this package writes a timestamped record to logs/sidewalk_bringup/, and adds one summary line to logs/RUNLOG.md. If you want to know what happened during an experiment, that is where to look.
