VSLAM Sidewalk Robot: Information Worksheet Flow

Handover for the student who continues Mitacs Globalink 2026 project 50124, "VSLAM-Based Navigation for Autonomous Sidewalk Robots". Thaw Zin (Suranaree University of Technology) with Prof. Moein Mehrtash, McMaster University. Written 29 September 2026, at the end of the project.

0How to use this page

Why you need this. The project ran for twelve weeks and left about 400 files of notes. You do not have time to read them. This one page tells you what was achieved, where every file and recording is, how to switch the robot on without breaking anything, how to run each workflow, and which mistakes have already been made so you do not repeat them.

Read section 1 first (10 minutes). Then, depending on what you want to do:

  • Re-analyse existing data without the robot: sections 2, 6 and 7, then the replay.sh and evaluate.sh parts of section 5.
  • Drive the robot: sections 3 and 4, then mapping.sh in section 5, and section 8 before your first drive.

Every technical word is explained in brackets the first time it appears and again in the glossary (section 10). Every number names the file it came from in small grey text. Wherever this page would need an address, a login or a key, it says ask Prof. Mehrtash or the lab: none of that is written here on purpose.

Plain terms: this is the map of the project, not the project itself. The project itself is the GitHub repository and the Autonomous Service Robot Teams folder named in section 2.

1Start here

Why you need this. Before touching anything you need to know what the robot can already do, how well, and where the evidence is. Otherwise you will re-measure things that are measured and trust things that were never proven.

1.1 What the project is

The question was: can a small delivery robot map a building and find its way around it using a stereo camera (a camera with two lenses 12 cm apart that measures depth the way two eyes do), helped by its own wheels, rather than expensive laser scanners or GPS?

The hardware is a Clearpath Husky A200 robot, a Stereolabs ZED X stereo camera on a 3D-printed mount, and an NVIDIA Jetson AGX Orin computer (a small computer with a graphics processor) that runs the camera and the mapping. The mapping program is RTAB-Map 0.21.13 (an open-source SLAM system; SLAM = simultaneous localisation and mapping, building a map while working out where you are on it), running on ROS 1 Noetic (the Robot Operating System, the message-passing framework robots use). A Kalman filter (a standard way of combining several noisy sensors into one best estimate) blends the camera's motion estimate with the robot's wheel odometry (distance counted from wheel turns) and gyroscope (a sensor that measures how fast the robot turns). Two LiDARs (laser scanners) on the robot's mast, processed with a colleague's self_navigation package used unchanged, give an independent second opinion on where the robot went. It is never called ground truth (section 7).

2.2 Where the recordings are: the Autonomous Service Robot Teams folder

Every recording and result is kept in the Autonomous Service Robot folder in Microsoft Teams (Microsoft's shared chat and file space). Ask Prof. Mehrtash (McMaster University) for access. Every folder path on this page and in data/DATA_INDEX.md is a path inside that Teams folder.

Getting a recording onto the Jetson for a replay. The Jetson does not read Teams itself, so the copy goes through any computer you have in the lab:

  1. In Teams, download the run's folder (for a drive: series2_raw/<run>/; for the camera depth study's station recordings: the files under paper_zedx_vs_lidar/) to your computer.
  2. Copy it to the Jetson over the lab network (the Jetson's address and login: ask Prof. Mehrtash or the lab). A SLAM drive goes into ~/replay_inputs/slam/<run>/, a camera bench recording into ~/replay_inputs/bench/: 
    rsync -s -av --progress s2_slam_01/ <user>@<jetson>:replay_inputs/slam/s2_slam_01/
scp w3_5.0m_burst01.svo2 <user>@<jetson>:replay_inputs/bench/
    what it does: copies the folder (or file) onto the Jetson's internal disk; -s keeps folder names with spaces in one piece. rsync (a copy program that can resume an interrupted copy) is better for big folders; scp (secure copy) is fine for one file.
  3. Check the copy arrived whole: compare the file sizes with data/DATA_INDEX.md (ls -l on the Jetson). A copy stopped half way is shorter than the listed size.
  4. Make sure at least 3 GB stay free on the Jetson after the copy (df -h ~), and delete the copy when you have finished with it: the Teams folder keeps the original.

3.2 Wiring

  • Camera to Jetson: GMSL2 into the Jetson's camera card. The camera needs two services on the Jetson (nvargus-daemon, zed_x_daemon) and the Jetson's own internal display session alive, even though no monitor is attached (automatic login keeps it up; the camera cannot open without it).
  • Jetson to robot: the USB-C cable. The robot's computer gets its wire address from the Jetson. No other computer may be cabled to the robot at the same time (it would take that address).
  • Power: Jetson and camera from the EcoFlow; robot from its own battery. The Jetson can therefore stay up while the robot is switched off to charge.
  • Network: Jetson and robot both on the same lab WiFi for drives (which network: ask Prof. Mehrtash or the lab); your computer reaches the Jetson's pages over the lab network. The robot's WiFi address changes every time it comes back from charging: check it before every session.

docs/OPERATIONS.md "Robot address changes after charging"; catkin_ws/src/sidewalk_navigation/doc/PROTOCOL.md step 1.

3.3 Switch-on order

  1. EcoFlow on, then the Jetson. Wait until it answers over the network. Check its uptime: if it has been up more than about 4-6 hours, restart it now, because camera freezes grow with uptime (0 in 3 min after a restart, 16 in 7 min at 20 h).
  2. Check the camera is present (/dev/video0 and /dev/video1 exist, both services active, a display session under /tmp/.X11-unix/). Do not open the camera yet.
  3. Robot on (its computer boots in about a minute). Joystick on and paired. Confirm the wheels answer the joystick.
  4. Plug the USB-C cable in at the robot only after the robot has booted. Check the wire answers from the Jetson.
  5. Check the robot's WiFi address and update the Jetson's ssh alias if it changed.
  6. Start the Jetson's helper pages (storage page, jobs page) if they are not running; they do not survive a reboot.
  7. Walk the route once before the robot: the corridor lights are motion-sensor controlled and a parked robot or empty corridor can be in the dark; a light switching on as the robot arrives changes the camera's exposure mid-drive. Note whether the lights were on.
  8. Park the robot on the start mark, facing east down the long corridor, exactly as every drive did. RTAB-Map anchors its map where the robot starts, so a different start silently offsets every number.

3.4 During a drive

  • Stand still at least 60 s at the start and at the end. The robot's gyroscope heading drifts about 3.5-5 degrees a minute even parked (UM7 gyroscope bias, compass off); the first minute measures that drive's rate so the blend can subtract it. The robot-side start script also re-zeroes the gyroscope while the wheels are still.
  • Slow: about 0.15 m/s; wide turns, about 20 degrees per second or less; never turn on the spot facing a wall closer than about 1.5 m (the camera ignores anything nearer than 1 m and sees nothing there).
  • Drive every lap the same way round. If you must come back along a corridor, come back in reverse without turning the robot round: the camera then still faces what it saw going in and keeps recognising places (section 8).
  • Every ~5 minutes make an extra 30 s stop (the blend re-measures the gyroscope).
  • Do not rescue a bad drive: a bad drive is a data point, a rescued one is not comparable.
  • The drive ends only when you say "park" (run/park.sh <run>); the map is then closed properly after 60 s of stillness. Standing still by itself never ends a drive.

docs/SOLVED.md; docs/ENGINEERING_NOTES.md section 2.13a.

3.5 Shutdown order

  1. Say "park"; wait until the jobs page shows the map closed properly (the corrected positions are written only at shutdown; a map not closed properly loses them and its word dictionary).
  2. Stop the robot side (run/robot_side.sh stop): it interrupts the LiDAR recording by exact process name so the bag closes properly.
  3. Run the integrity check on the database and the bag now, not tomorrow (a memory card damaged four files at rest in this project).
  4. Unplug the USB-C cable at the robot BEFORE switching the robot off. Twice the Jetson became unreachable when the robot was switched off with the cable in, and had to be power-cycled (its address requests every 7 s, then silence).
  5. Robot off, then charge it. Tell whoever is around that the robot is off while charging.
  6. Jetson: leave it running for replays and file copies, or shut it down cleanly (never pull the EcoFlow's plug: an unclean stop has cost a database).

docs/SOLVED.md "Ctrl+C on a mapping run can leave a database with no map"; docs/ENGINEERING_NOTES.md rule 7.

5.1 What is common to every workflow

  • Watching: every job writes a one-line .progress file next to its output (for example NEURAL_PLUS 47/180 893s); the jobs page on the Jetson finds those files by itself and draws a bar and time left; liveness is judged by the file's freshness, never by searching for a process name. The live map page shows the camera map (left) and the robot's live LiDAR view (right), refreshed every 1-2 s, with red banners for TRACKING LOST and CAMERA DOWN. Page addresses: the Jetson's address with the ports 8095 (live map), 8096 (jobs), 8092 (storage); the address, and the link to the project website served by the Jetson, from Prof. Mehrtash or the lab.
  • Never find or kill a process with pgrep -f / pkill -f or any "contains the name" test: it matched itself and reported dead jobs alive six times. Compare whole argument names; test every check against a name you know is absent.
  • Everything starts detached (setsid nohup) so a dropped connection changes nothing; a job that outlives one command gets a watcher that reports failure and silent death, not only success.
  • A results pack per run (results/<series>/<run>/RESULTS.md): both gap kinds with closure counts, the per-turn table, link statistics, tracking losses, camera outages (count, seconds, distance driven blind, resets per 100 m), processor load, the figures, the timelapse. Every number names its file.
  • Run ids: s2_static_NN (mapping drives), s2_loc_NN, s2_slam_NN, s2_nav_NN, s2_scale_NN; the scripts refuse an id whose database already exists.

docs/ENGINEERING_NOTES.md rules 8, 13, 22; the header of tools/drive/camera_guard.py.

5.5 run/evaluate.sh <run>: score a run

Purpose: turn a run's database, recording and LiDAR estimate into the results pack.

It does, in order: check_closed.py (was the map closed properly? corrected positions present?); db_to_tum.py (tracking-alone path from Node.pose); db_corrected_tum.py (corrected path from Admin.opt_poses) or, if the map was not closed, optimize_graph_se2.py (re-optimise from the links; validated to 0.35 mm); closure counts from the Link table (types 1 and 2, each pair counted once: rows are stored twice); compare_lidar.py (pairs positions within 0.05 s, rigid fit with no rescaling, median and 95th percentile; refuses a LiDAR estimate that failed its own check); the per-turn table; camera outages and freezes; then the RESULTS.md writer and figures. grep -c "cannot be used" mapping.log must be 0 or the run is invalid (silent feature-detector downgrade).

Good looks like (drive 10): closed properly; corrected gap a few centimetres with the number of end-to-start closures stated; 0.2-0.7 m median from the LiDAR; 0 camera crashes; freezes under 2 s. 5.8 run/localise.sh <run> [map]: find itself on a saved map (robot)

Purpose: load a finished map (drive 10's master copy) with map-building off and see whether, and how fast, the robot recognises where it is.

  • Everything of 5.7's checklist. The master map is read-only and is never passed to RTAB-Map itself; the script makes a working copy (passing the master's path to load_database with clear: true would erase it).
  • Decide the starting guess before the session: KIDNAP_PRIOR="40 40 0" (40 m outside: every fix must come from real recognition) or "0 0 0" (on the start mark, as navigation uses).

7The evaluation method

Why you need this. There is no ground truth in the building. Every number therefore depends on how it was checked, and anyone reading the numbers will ask. The rules below are the ones the project's numbers were produced under; a new number produced under different rules cannot be set beside them.

7.1 The LiDAR reference and its limits

  • What it is: the colleague's self_navigation LiDAR mapping (RTAB-Map in LiDAR mode: Helios packets decoded, re-stamped, the robot's own body filtered out, box-cropped, then rtabmap_3d.launch with Reg/Strategy=1), replayed from the recording with one setting added, Reg/Force3DoF=true. It takes the wheels + gyroscope path (/odometry/filtered) as its odometry and does not refine neighbour links, so between LiDAR loop closures it IS the wheel path; the scans correct it only where they match a place seen before.
  • Write it as "agreement with the independent LiDAR estimate", never "error" or "ground truth". The project's own evaluation code lists another SLAM stack as cross_stack and deliberately excludes it from the kinds of truth that count (only motion capture, RTK GNSS and simulator truth do).
  • Its own check first: it is used only if it ends within about 0.5 m of its start with LiDAR closures of its own. It failed on drives 1, 2 and 7 (0 closures), on drive 6 and 8 unflattened (tilted maps: 2.14 m, 4.73 m), on localisation session 3 (wall-fit drift 0.126 m against 0.10) and on the SLAM session (0.52 m).
  • Its uncertainty, stated beside every figure: range noise 15-30 mm; the two LiDARs agree to about 5 mm; its size comes from the wheels, which read 6.2 % long on a taped 15 m; the LiDAR-to-camera mounting offset was never measured; on the same route drives 4 and 8 agreed with it to 0.24-0.26 m median, which is why the localisation line W4 was set at 0.50 m and not tighter.
  • How the comparison is made: positions paired within 0.05 s (the once-a-second LiDAR nodes filled in with the 50 Hz wheel stream, or only about 10 % pair up), lined up by rotation and shift only (SE(3), never with a scale factor: a stereo camera measures true size), distance reported as median and 95th percentile, never RMSE alone.

7.2 The two kinds of start-to-end gap

A database's Node.pose is the robot's tracking alone; loop closures never change it. The map's corrected positions are Admin.opt_poses, saved only when the map is shut down properly, or a re-optimised graph from optimize_graph_se2.py. Anything drawn from db_to_tum.py or render_map.py is the first kind unless it says otherwise. Report both, labelled, and never plot them on one axis. A corrected gap always carries its closure count and how many closures join the end straight to the start: drive 1's 0.056 m came from a single end-to-start closure that moved points up to 39.9 m, so it says nothing about the middle of the map. In a fused drive the nodes carry the blend's position, and the camera's tracker restarts from the blend each time it gives up (180 times on drive 10), so "camera tracking alone" on a fused drive is not an independent camera path. Parking on a tape mark by eye is only good to 20-50 cm, so a corrected gap of a few centimetres shows the map closed its own loop, not that the robot was parked that precisely.

7.4 The uncertainty rules (never compare against zero)

  • Two measurements of the same thing will never be exactly equal. State the uncertainty of each source before comparing: tape to a housing edge about ±5 mm; a box drawn by eye on an image about ±10 px (±20 mm at 2.5 m); factory calibration about 1 %; a depth reading's measured spread per surface; tape-mark parking 0.2-0.5 m; the robot's heading drift about 5 degrees a minute.
  • Two independent sources agree if their difference is less than about the square root of the sum of the squared uncertainties. Say "agrees to within X" or "disagrees by X, which is N times the combined uncertainty"; never bare "matches" or "is wrong".
  • Do not chase a difference smaller than the combined uncertainty; do chase one several times larger (the wheels' +0.94 m on 15 m was five times the parking spread, and real).
  • Every figure carries its spread: median with range, or a quantile. Never N = 1 without saying so; minimum N = 5 for a claim, median with (min-max), valid/total run count.
  • Judge every run against pass lines written before it. If the LiDAR estimate failed its own check, the accuracy lines are "not scorable", not "passed".

our small program pair that copies the robot's wheel and gyroscope readings to the Jetson over the USB-C wire (sender on the robot, receiver on the Jetson); it publishes nothing on the robot.

RTAB-Map was shut down through its normal path, so the database holds the corrected positions and the word dictionary; checked by check_closed.py.
Corrected gap / tracking-alone gap
the two kinds of start-to-end distance (section 7.2).
Costmap
a grid that marks how risky each 5 cm square of the floor is for the route planner.
Depth mode
one of the five ways the ZED X computes depth (QUALITY, PERFORMANCE, ULTRA, NEURAL, NEURAL_PLUS); all drives used NEURAL.
Depth cutoff / min_depth
the camera ignores anything nearer than 1 m; the map uses depth only to 3 m since drive 10.
EKF, Kalman filter
a standard method for combining several noisy sensors into one best estimate.
evo
a trajectory-comparison tool that measures how closely two recorded robot paths agree (pinned at 1.31.1).
Fix (localisation)
a moment RTAB-Map accepts where the robot is on a saved map, after at least 20 matching 3D points between the new picture and a map picture.
Force3DoF (Reg/Force3DoF=true)
keep the map on the floor plane: it may slide and turn, never tip.
fusion.bag
the Jetson's recording of every position stream during a run (a ROS bag: a timed log of messages).
GEN_1 / GEN_2
the ZED camera's two built-in position-tracking methods, a camera setting; GEN_2 is the default.
GMSL2
the camera cable standard the ZED X uses (not USB).
Ground truth
an independent measurement of where the robot really is (motion capture, RTK GNSS, or a simulator's truth). The building has none; the LiDAR estimate is not it.
Gyroscope
a sensor that measures how fast something turns; the robot's (UM7) drifts about 5 degrees a minute; the camera has one too.
IMU
inertial measurement unit: a gyroscope plus accelerometers in one chip.
Jobs page
the Jetson's web page that finds every running job by its .progress file and draws a bar (port 8096).
LiDAR
a laser scanner that measures distance by timing reflected laser light (Helios 32 and Ouster OS1-32 here).
LiDAR estimate / yardstick / reference
the robot's path from the colleague's LiDAR mapping, used as an independent second opinion (section 7.1).
Live map page
the browser page showing the camera map and the LiDAR view during a drive (port 8095).
Localisation
working out where the robot is on a finished map, without changing the map.
Loop closure
the map recognising a place it has seen before and pulling itself straight; counted as Link table types 1 (recognised again) and 2 (nearby re-match).
LoopThr (Rtabmap/LoopThr)
how sure RTAB-Map must be before it uses a recognised place; 0.08 in localisation and SLAM sessions.
Mask / people blanking
zeroing the depth pixels inside the camera's person boxes so people leave no trace in the map.
move_base
the standard ROS route planner (dynamic window approach: choosing speed and turn several times a second to follow the route without hitting anything).
Node
one saved map snapshot: a picture plus the position it was taken from; the graph is the nodes and the links between them.
Odometry
step-by-step position tracking (from wheels, or from pictures: visual odometry); never corrected by itself.
Park
the word that ends a drive; the map is closed after 60 s of stillness.
Pass line
a success criterion written before the test, with what passing and failing mean.
Perceptual aliasing
different places that look the same (the identical signboards).
Progress file
a one-line text file a job rewrites every ~30 s (N/M and seconds elapsed) so the jobs page can show it.
Results pack
the small folder per run with the numbers, figures and timelapse.
ROS, ROS master, topic
the Robot Operating System: programs exchange named message streams (topics) through one coordinating program (the master).
RTAB-Map
the open-source SLAM program used throughout (0.21.13 on the Jetson, 0.21.10 on the robot).
SE(3) alignment
lining two paths up by rotation and shift only; Sim(3) also allows a size change and is not used for scoring.
SLAM
simultaneous localisation and mapping: building the map while working out where you are on it.
SVO / .svo2
the ZED camera's own recording format: stereo pictures and IMU, no depth (depth is recomputed at playback).
tegrastats
NVIDIA's once-a-second log of the Jetson's processor, GPU, memory and power.
TF
ROS's shared table of where each part of the robot is relative to the others (map -> odom -> base_link).
TUM format
a path file: time x y z qx qy qz qw per line.
Twist mux, /cmd_vel
the robot's command switch: joystick and e-stop rank above our navigation commands.
/use_sim_time
the ROS setting that makes programs follow a recording's clock; true only on a replay master.
Wall fit
the registered way of lining a session's LiDAR map up with a reference map to check the LiDAR's own drift.
